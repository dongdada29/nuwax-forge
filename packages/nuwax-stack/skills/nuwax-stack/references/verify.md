# 行为验证

先读取任务的可检查完成条件与目标仓现有验证入口，选择能区分修复前后的最小验证。分析任务没有执行授权时只给方法；实施任务已有范围内授权时直接执行所需验证，不逐条重复询问。

验证环境需要明确：如何启动、如何判断健康、如何驱动目标行为、如何保存证据、如何清理本轮资源。复用仓内验证技能或脚本；缺少时在本任务的隔离工件区补齐，不覆盖他人配置或启动共享服务。

已有固定配方时按 [验证结果契约](verification-contract.md) 导入结构化证据，避免再由模型解析整份日志和手工拼接完成状态。配方失败先区分产品、环境与验证器问题。

每项功能对应一个行为证据：入口/前置条件、操作、期望结果、实际结果、产物位置、执行时间、分支/HEAD及相关脏文件。修复应有能证明原缺陷、并在修复后通过的验证；纯文案或可逆的小调整不制造无意义测试。

命令测试、浏览器、真实设备、安装包和线上行为是不同证据。只证明其中一层时清楚写出边界。测试可能写缓存、产物或数据库，执行前确保该副作用属于当前授权和隔离环境。

验证失败时把可复核输出交回执行循环，不修改期望来放行。外部条件不具备时记录受阻或待验收，不能将“没有发现问题”记成验证通过。

结果和个人状态只写自有台账。团队原始需求或问题文档保持只读。完成条件要求线上或设备验收时，本地成功不能把个人任务直接标完成。
